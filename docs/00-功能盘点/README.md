| 批次 | 依次排查 | 这样安排的原因 |
| --- | --- | --- |
| 第一批 | 01 Harness → 03 工具、权限与 MCP → 09 输入输出与事件 | 三次调查沿用同一次工具审批案例。01 查主循环怎样继续，03 查允许或拒绝由谁决定，09 查用户决定如何回到对应调用。 |

## 调查时核对什么

选一个有代表性的操作，沿实际入口追到结果。首个样例可沿 Harness 的“用户发起任务 → 工具请求审批 → 用户批准或拒绝 → 结果回写 → 会话保存”核对以下六点。

| 维度 | 要弄清的问题 |
| --- | --- |
| 职责与边界 | 模块接收什么、产出什么，在哪一步将控制权交给谁？ |
| 入口与触发 | 谁在什么时候调用它，受哪些配置、权限和运行条件影响？ |
| 核心流程与事件 | 哪几个步骤改变了结果？关键变化是静默执行、打印、回调还是结构化事件？能否关联到具体任务和工具调用？ |
| 关键判断 | 哪些分支由代码规则、模型、配置或用户决定？例如，谁提议写入 Skill，谁最终允许写入？ |
| 状态与隔离 | 状态在哪里创建、更新、持久化和清理？检查全局缓存、进程内对象和固定路径，判断不同用户、项目或同一用户的并发会话会共享什么。 |
| 失败、中断与恢复 | 分别核对页面刷新后能否重连和审批、后端重启后能否从中断处接续且避免重复执行、任务结束后能否重放工具调用和审批记录。 |

## 专题文档怎么写

- **核心结论放在开头。** 用一个短段落说清模块提供什么能力、通过什么机制实现、在哪些条件下生效。同一模块中完成程度不同的能力分别说明。
- **原理只留决定行为的部分。** 用一条短调用链或几条要点交代入口、关键判断和状态去向。六个维度供调查时核对，正文按本模块的重要性取舍。跨模块机制链接到负责该机制的专题。
- **证据紧跟结论。** 优先链接关键源码函数或已有验证记录，标明“源码确认”“运行验证”或“待验证”。实测时保留影响结论的环境、结果和必要的复现入口。省略搜索过程、逐文件阅读笔记、完整日志和大段源码。
- **篇末只留影响后续开发的事项。** 写清可复用入口、影响 Web 接入的具体依赖或缺口，以及最值得验证的行为。例如，“已保存对话历史；进程重启后能否恢复待审批调用仍待验证”。
