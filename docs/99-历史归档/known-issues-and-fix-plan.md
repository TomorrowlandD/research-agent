## 1. Windows 单文件搜索错误返回无匹配

**状态：已修复，离线验证和真实会话补测均通过。**

- 现象：`grep_search` 使用 `path="agents/agent.py"` 搜索上述关键词时返回 `No matches found`；使用 `path="agents"`、`include="agent.py"` 则正常命中。
- 原因：`agents/tools.py` 中 `_grep_search()` 在 Windows 使用 `_grep_python()`，后者只调用目录遍历，没有处理文件路径。目录访问异常被忽略，最终被误报为无匹配。工具定义本身允许传入文件或目录，因此这是实现缺陷。
- 影响：模型可能将搜索失败误判为代码不存在。测试日志中“第一阶段尚未实现”的结论因此错误。

**修复方案：** 在搜索入口区分文件和目录。单文件直接逐行匹配，目录沿用遍历；不存在、不可访问或正则无效时返回明确错误，不能统一当作无匹配。保留现有 `include` 过滤和结果数量限制。

**验收：** Windows 下单文件和目录搜索都能命中已知关键词；真正无匹配与路径错误能区分。

修复前的临时绕过：使用 `path="agents"`、`include="agent.py"`。修复后不再需要绕过。

**本次实现：** Python 搜索已区分文件与目录，并复用逐行搜索逻辑；路径不存在、无效正则和读取失败返回明确错误，部分文件无法读取时保留已有命中并提示搜索不完整。保留过滤规则与数量限制，单文件路径不再需要绕过。

**真实补测：** 直接使用 `path="agents/agent.py"` 搜索 `BEAR_DEEPSEEK_THINKING`，成功返回第 291、294、300 行；扩展关键词搜索也正常命中。

## 2. 中文文件读取乱码

**状态：已修复，离线验证和真实会话补测均通过。**

- 现象：`read_file` 读取 UTF-8 的 `PLAN-deepseek-v4-pro.md` 时，中文显示为乱码；使用明确 UTF-8 编码读取原文件则正常。
- 原因：`agents/tools.py` 的 `_read_file()` 和 `_grep_python()` 使用 `read_text(errors="replace")`，未指定编码。Windows 默认编码可能与文件编码不同，而且替换错误字符会掩盖解码失败。
- 影响：模型接收到的文本可能已经损坏，影响文件理解和搜索结果。不能据此认定原文件是 GBK。

**修复方案：** 为读取和搜索共用文本读取策略，优先使用 `utf-8-sig`（兼容普通 UTF-8 和 BOM）。若需支持旧编码，明确提供编码配置或受控回退，并提示所用编码；不要直接静默替换损坏字符。

**验收：** 中文 UTF-8、带 BOM 的 UTF-8 和英文文件读取正常；中文关键词搜索可命中；无法解码时有清晰提示。

**本次实现：** `_read_file()` 与 Python 搜索共用 `_read_tool_text()`，使用 `utf-8-sig` 严格解码。无法解码时明确报错，不静默替换；本次没有增加 GBK 等旧编码回退。

**真实补测：** 用户最新日志中计划标题、日期及中文正文均正确显示，没有此前的乱码。

## 3. 大文件反复读取仍被截断

**状态：已确认，待改进。**

- 现象：模型要读取 `agent.py` 第 279 行附近，但多次 `read_file` 都只得到文件开头；读取保存的结果文件仍再次被截断，不能获取目标内容。
- 原因：`read_file` 仅有 `file_path` 参数，不支持按行读取；`agents/agent.py` 的 `_persist_large_result()` 对超过 30 KB 的结果持久化，仅返回前 200 行预览，却提示再次读取完整结果。
- 影响：模型陷入重复调用，增加输入用量，最后可能根据不完整证据回答。持久化本身是合理机制，但缺少分段读取配套。

**修复方案：** 为 `read_file` 增加可选的 `start_line`（从 1 开始）和 `max_lines`，同步更新工具定义与实现。限制每次返回的字符或字节量，并提示总行数及下一段位置。更新超长结果提示，指导分段读取，而不是再次读取整个文件。保持旧调用参数兼容。

**验收：** 能直接读取第 279 行附近；超过单次预算时可以继续分页；不反复返回开头，不重复持久化整份结果；边界和无效行号有明确处理。

临时绕过：目录搜索定位代码；必要时由用户在本地按行读取。无需为了验收重复读取整份大文件。
